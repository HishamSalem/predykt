# Contributing to predykt

## Development setup

```bash
git clone https://github.com/HishamSalem/predykt
cd predykt
python -m venv .venv && . .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev,test,plot]"
pytest -q
```

`pip install -e .` is not optional for development: `predykt/_version.py` is generated by
setuptools-scm at build time and is gitignored, so an editable install is what makes the
version resolvable. The package no longer *fails* to import without it — there is a
fallback chain — but you will get `0.0.0.dev0` instead of a real version.

## Tests

```bash
pytest -q                  # everything (~70s)
pytest -q -m "not slow"    # skip the calibration sweeps (~10s)
```

The `slow` marker is registered in `pyproject.toml`. It covers the tests that fit models
over many datasets to measure rejection *rates* rather than a single outcome. Both forms
must pass — CI runs the full suite, but the fast form has to stay usable locally.

### Writing tests for the statistical machinery

Do not assert a significance verdict on a single dataset draw. At `alpha=0.05` such an
assertion is false a few percent of the time by construction, and it will fail
intermittently in CI — or deterministically on somebody else's library versions, which is
worse, because it looks like a real regression. Two things that were measured here:

- The null pair's p-value ranges 0.016–0.984 across dataset seeds, crossing alpha on 2 of
  10, while the effect-size ratio `observed / null_mean` stays cleanly separated
  (6.6–8.8× true vs 0.7–1.5× null).
- The same code and the same seed produce p=0.115 on one machine and p=0.033 on another,
  purely from a different xgboost build.

So: assert the **mechanism** (effect sizes, orderings, invariants) in fast tests, and
assert **rates over many datasets** in `slow` tests. Measure Type-I error on a DGP where
H₀ genuinely holds for every pair, not on one where a strong interaction elsewhere can
leak into the pair under test.

## Linting

CI gates on error-level rules only:

```bash
ruff check predykt tests --select F,E9
```

This must pass. It is the same command `.github/workflows/ci.yml` runs.

**Bare `ruff check` will report far more.** The `[tool.ruff.lint]` config selects
`E,F,I,B,UP`, which currently reports **147 findings (121 auto-fixable)** — mostly
`UP006`/`UP045` (PEP 585/604 annotation modernisation), `I001` (import sorting), and a
handful of `E501` long lines. That gap is deliberate: the style backlog predates the
current CI gate, and clearing it with `ruff check --fix` would rewrite nearly every file,
destroying `git blame` and burying substantive diffs.

If you want to clear it, do it as a **separate, isolated commit** that contains nothing
else, so it can be skipped with `git blame --ignore-rev`. Do not mix cosmetic reformatting
into a behaviour change.

## Line endings

`.gitattributes` normalises everything to LF in the repository. Git will still check out
CRLF on Windows if that is your `core.autocrlf` setting; that is fine and expected. If you
see a file show up as entirely rewritten in a diff, run `git add --renormalize .` rather
than committing the churn.

## Release process

**A git tag must exist before `python -m build`.**

On an untagged checkout setuptools-scm resolves to `0.0.0.devN+g<hash>`. The `+g<hash>`
local version segment is rejected outright by the PyPI upload API — PEP 440 local versions
cannot be published. This is a useful safety net, not a bug: it is what stops an untagged
build from being uploaded by accident.

`fallback_version` in `pyproject.toml` does **not** suppress it. That setting only engages
when setuptools-scm cannot detect a version at all — i.e. when there is no `.git` directory,
as when building from an sdist or a downloaded zip, which would otherwise raise
`LookupError` and fail the build. Measured behaviour:

| Checkout state | Resolved version |
|---|---|
| untagged git checkout | `0.0.0.devN+g<hash>` — **PyPI rejects this** |
| tagged `v0.2.0` | `0.2.0` |
| no `.git` at all | `0.0.0.dev0` (via `fallback_version`) |

Steps:

```bash
# 1. Land everything, update CHANGELOG.md and the version in CITATION.cff.
# 2. Tag, then build.
git tag v0.2.0
python -m build

# 3. Confirm the artefact version has no local segment — no "+" in the filename.
ls dist/          # predykt-0.2.0-py3-none-any.whl, predykt-0.2.0.tar.gz

# 4. Upload.
twine upload dist/*
```

After uploading, check the rendered project page on PyPI. The long description is taken
from `README.md` at build time, so a README fix only reaches users once a release ships —
fixing `main` does not change the live page.
